# JAF モータースポーツ諸規則アプリ 再設計メモ

対象: <https://jp.motorsports-regulations.org/>（GCP Cloud Run / project `gen-lang-client-0036162343` / us-west1）
リポジトリ: `maruyamah-duxi/motorsports-regulations`

---

## 1. 現状の何が問題だったか

AI Studio が生成した初版は **静的な React アプリに規則本文をベタ書き** した構成でした。

| 症状 | 直接の原因 |
| --- | --- |
| JAF の更新に追いつけない | `data_part1.ts` / `data_part2.ts` に本文が手書きで埋め込まれている。JAF 側が PDF を差し替えても何も起きない。取り込まれているのは **5 件のみ**（JAF の配布は国内 125 件 + 国際 35 件）。 |
| PDF 全文がテキスト化できていない | 変換工程が存在せず、LLM に要約させた文章が貼られている。原本との一致が保証されない。 |
| 画像が PDF と同じように出せない | 画像抽出そのものが無い。加えて、JAF の車両規則の図は大半が **ベクタ描画** なので、一般的な「埋め込み画像を取り出す」方式（`get_images()` 等）では 1 枚も取れない。 |

つまり **データ生成パイプラインが無い** ことが根本原因で、UI をいくら直しても解決しません。
そこで「PDF → 構造化データ」を作る工程を新設し、アプリはその生成物を読むだけにします。

## 2. 全体アーキテクチャ

```
                        ┌────────── GitHub Actions (毎週月曜 03:10 JST) ──────────┐
motorsports.jaf.or.jp   │  1. crawl    諸規則ページを解析 → catalog.json          │
  /regulations/…  ──────▶  2. diff     アップロード日 + SHA-256 で差分判定        │
  （国内 / 国際）        │  3. convert  変更分だけ PDF → document.json + 図版     │
                        │  4. index    index.json / 更新履歴 / 検索インデックス     │
                        │  5. commit   生成物を git に、図版は GCS へ            │
                        └───────────────────────┬────────────────────────────────┘
                                                │
                        ┌───────────────────────▼────────────────────────────────┐
                        │ Cloud Run (既存)                                        │
                        │  ├ 静的配信 (React SPA)                                 │
                        │  ├ /api/search  … SQLite FTS5 (trigram) 全文検索        │
                        │  └ /api/ask     … RAG。規則本文を根拠に引用付きで回答   │
                        └─────────────────────────────────────────────────────────┘
                                     ▲                        ▲
                              GCS: 図版・原本 PDF 保管    Gemini API（鍵はサーバ側のみ）
```

原則:

- **生成物は決定的**。同じ PDF からは同じ JSON が出る（`pipelineVersion` で世代管理）。
- **アプリは変換結果を読むだけ**。UI の改修とデータ品質の改善を分離する。
- **原本 PDF は git に入れない**。JAF の著作物なのでキャッシュは CI の一時領域と GCS に留め、リポジトリには変換結果とメタデータのみ置く。

## 3. 更新追従（課題①）

### 実測した制約

JAF の PDF レスポンスは以下でした（2026-09-09 実測）:

```
cache-control: no-cache, no-store
content-type: application/pdf
（ETag なし / Last-Modified なし）
robots.txt: 404
```

**条件付き GET が使えません。** よって次の 2 段構えにします。

1. **一覧ページの「アップロード日」** — `p._date` に `アップロード日：2026年9月9日` が入っている。
   ここが変わったものを第一候補にする。
   さらに「最近のアップデート」タブは全件をアップロード日の降順に並べた実質の更新フィードなので、
   カテゴリ一覧と突き合わせれば取りこぼしを検出できる。
2. **本体の SHA-256** — 日付据え置きでの差し替えを拾う。ダウンロードは避けられないので、
   1.5 秒間隔・連絡先入り UA で夜間に静かに巡回する。

### 差分の見せ方

`data/changes/YYYY-MM-DD.json` に「追加 / 更新 / 削除 / 失敗」を残し、
コミットメッセージと GitHub の Job Summary に反映します。
将来的に、更新前後の `document.json` を条単位で突き合わせれば
**「第◯条のここが変わった」という改正差分ページ** が作れます。
これは JAF 自身が提供していない機能で、このサービスの一番の売りになり得ます。

### JAF サイトの DOM（クローラが依存している構造）

```
div.tab-menu
 ├ ul._header > li.js-slideTab-header        「カテゴリ一覧」「最近のアップデート」
 └ div._content.js-slideTab-body [0]         ← カテゴリ一覧
    └ div#01 … div#05                        大分類（h2.heading-primary）
       └ div.togglegroup > div.toggle-accordion
          ├ div._header                      中分類
          └ div._content > ul.list-type-iconBlock > li > a[href$=".pdf"]
                                             p._title / p._date
```

Sitecore 由来の安定した構造ですが、リニューアルで壊れる可能性はあります。
**取得件数が前回比で 3 割以上減ったら異常として落とす** ガードを CI に入れておくのが安全です。

## 4. PDF → HTML 変換（課題②・③）

`pipeline/jafreg/layout.py` が中核です。

### 4.1 本文の抽出と読み順

- PyMuPDF の `get_text("dict")` でブロック / 行 / スパンを取得（bbox・フォント・サイズ付き）。
- **XY-Cut** を再帰適用して段組と読み順を復元。1 段組でも 2 段組でも同じコードで通る。
- **ヘッダ・フッタ除去** は位置だけで判定しない。天地 12% の帯にあり、かつ
  数字を伏せた文字列が全ページの半数以上で繰り返され、かつ本文サイズ以下のものだけを落とす。
  （位置だけで切ると、ページ先頭に来た「第◯章」を巻き添えにする。実際に試作中に踏んだ。）
- **見出し** は「第◯編 / 第◯章 / 第◯条 / 1-1 / 附則 / 別表」等の採番パターンを第一優先、
  フォントサイズ比を第二優先で判定。見出しには安定したアンカー ID を振り、
  **AI 回答や検索結果から条単位で直リンク** できるようにする。

### 4.2 図版（ここが肝）

「埋め込み画像を取り出す」発想を捨てて、**図版が占める領域を決めてページごと切り出す** 方式にしました。

1. ラスタ画像の配置矩形（`page.get_image_info()`）
2. ベクタ描画のクラスタ矩形（`page.cluster_drawings()`）
3. 1 と 2 を近接マージして「図版領域」を確定
4. 罫線・下線（辺が 24pt 未満）、ページ枠（面積比 92% 超）、表として検出済みの領域を除外
5. 残った領域を `page.get_pixmap(clip=…)` で 200dpi ラスタライズ → WebP

この方式なら、線画・寸法線・図中の注記文字がまとめて 1 枚に収まり、**PDF と同じ見た目** になります。
ベクタ図しか無い車両規則でも図が取れるのはこのためです。

### 4.3 図と本文の対応付け

- 図版領域を **1 つのブロックとして本文ブロックと同じ読み順ソートに混ぜる**。
  これだけで「図が本文の正しい位置に入る」が成立します。
- 図版領域の内側に落ちた文字ブロックは本文から除外（図に描き込まれた文字の二重出力を防ぐ）。
- 直前・直後 60pt 以内にある `図◯` `表◯` `写真` で始まる行をキャプションとして図に結びつける。
- 各ブロックに `page` と `bbox` を残すので、後から
  「この段落は原本 P.42 のここ」というハイライト表示や原本ページ並置ができます。

### 4.4 表

`page.find_tables()` でセル配列として取り、HTML の `<table>` にします。
検出に失敗した表は 4.2 の図版扱いに落ちるので、**最悪でも画像として本文の正しい位置に残ります**。

### 4.5 テキスト層が無い / 文字化けする PDF

- ページの抽出文字数と「文字化け率」（U+FFFD・私用領域の比率）を測り、
  閾値を超えたら `warnings` に記録し、HTML 上部に「原本を確認してください」の注意を出す。
- `--ocr` で tesseract（`jpn` + `jpn-vert`）による OCR フォールバックに切り替え。
- 古い年式の PDF（2012 年頃）はスキャン由来の可能性があるため、初回同期のログで要確認。

## 5. データモデル

```
data/
  catalog.json          JAF ページから拾った配布物一覧（毎回上書き）
  state.json            docId → sha256 / uploadDate / 変換統計（差分判定の基準）
  index.json            フロントが最初に読む軽量インデックス（目次 40 件まで）
  changes/YYYY-MM-DD.json  その日の差分
content/<docId>/
  document.json         構造化本文（ブロック配列 + 目次）。**配信しない**
  assets/fig-pNNNN-MM.webp   図版。これだけ配信する
```

`document.json` は検索インデックスと目次の元で、**公開配信はしません**
（2026-09-11 以降。下の 7-f）。以前あった `index.html`（単体で読める全文
HTML）は生成をやめて削除しました。

`docId` は PDF URL のファイル名 + パスの SHA-1 先頭 6 桁。
JAF は改訂時にファイル名を変える（例: `…_20250101.pdf` → `…_20270101.pdf`）ため、
**同一規則の年度違いは別 docId** になります。年度をまたぐ紐付けは
**PDF のファイル名から作る系列キー**で行います（下の 7-b）。
当初はタイトルから年月日を落とす案でしたが、FIA の「競技規則_日本語版」が
4 本とも同名で別物を束ねてしまうため、ファイル名側を使っています。

`document.json` のブロック:

```jsonc
{ "type": "heading",   "level": 4, "text": "第12条 安全ベルト", "id": "第12条-安全ベルト", "page": 42, "bbox": [...] }
{ "type": "paragraph", "text": "…",                             "page": 42, "bbox": [...] }
{ "type": "figure",    "asset": "assets/fig-p0042-01.webp", "caption": "図3 取付角度", "page": 42, "bbox": [...] }
{ "type": "table",     "rows": [["項目","値"], …],              "page": 43, "bbox": [...] }
```

## 6. 検索と AI Q&A

### 検索

日本語全文検索をクライアント側で持つと、160 本 × 数百ページではインデックスが重すぎます。
Cloud Run 上に **SQLite FTS5 + trigram トークナイザ** の DB をイメージに焼き込む方式を推奨します。

- 外部サービス不要・追加費用ゼロ・数十 ms で返る
- 分かち書き不要（trigram なので「安全ベルト」でも「全ベル」でも当たる）
- ビルド時に `content/*/document.json` から生成するだけ

### AI Q&A（RAG）

現状の実装は**規則のタイトルと要約だけ**を system prompt に流し込んでいるため、
条文の中身を答えられません。RAG に置き換えます。

1. `document.json` を **条（見出し）単位**でチャンク化。メタデータに規則名・条番号・ページ・アンカーを持たせる。
2. Gemini の埋め込みでベクトル化し、FTS5 と同じ SQLite に格納（`sqlite-vec`）。
3. 質問 → ハイブリッド検索（全文 + ベクトル）→ 上位チャンクを根拠として渡す。
4. 回答には **必ず「規則名 第◯条（P.◯）」の出典を付け、HTML アンカーと原本 PDF の両方にリンク**。
5. 根拠が見つからないときは「該当なし」と答えさせる（規則の質問で作話は致命的）。

> セキュリティ注記: 現行リポジトリの `vite.config.ts` は `process.env.API_KEY` を
> **クライアントバンドルに埋め込む** 設定です。デプロイ済みの Cloud Run 版は
> AI Studio が用意した `/api-proxy` 経由でプレースホルダに置き換わっていたため
> 現時点で鍵は露出していませんが、自前でビルドし直すと露出します。
> RAG 化に合わせて **Gemini 呼び出しは必ずサーバ側**に移してください。

### 検索結果の見せ方: 拾って並べ、前後は原本へ（2026-09-11）

このアプリの出発点は「装備品や車両規定を調べたいのに、PDF が分散していて
必要な情報にたどり着けない」でした。**横断検索は「全文をインデックスに
持つこと」で成立していて、「全文をページとして公開配信すること」とは
別だ**というのが、9 章の検討を経て整理した点です。前者は残し、後者は
原本に渡す形に寄せています。

#### 散らばり自体を最初に見せる

実測すると、装備品は本当に散らばっています。

| 語 | 該当文書 | 該当箇所 |
| --- | --- | --- |
| 安全ベルト | 29 | 130 |
| ヘルメット | 50 | 227 |
| ロールケージ | 19 | 65 |
| 消火器 | 39 | 181 |

「安全ベルト」は 7 区分にまたがり、最多は **FIA 国際競技規則付則 J 項の
38 箇所**でした。調べ始める側からすると「付則 J 項を開く」という発想に
到達できないのが問題の本質で、どれを開けばよいか知るには先に全部の中身を
知っている必要がある、という鶏と卵になっています。

そこで `/api/search` は**表示中のページではなく全ヒット**を規則ごとに
集計した `byDoc` を返し、画面の先頭に区分つきで並べます（行を押すと
その規則だけに絞り込む）。件数の分布そのものが答えの一部です。

#### 抜粋は窓で切る

FTS5 の `snippet()` は trigram トークナイザだと 64 トークン＝実質 64 文字が
上限で、並べて判断するには短すぎました。一方でチャンク全文（中央値 510 字）
を返すと条をそのまま載せることになります。該当語の前後を切り出す窓
（前 120 字 / 後 220 字）に替え、前後や全文は原本へ送っています
（`server/excerpt.py`）。

ここは位置合わせに細工が入っています。全角で書かれた原文（`１０６,７００`）を
半角のクエリ（`106,700`）で引くには正規化した側で探す必要がありますが、
**画面に出すのは原文でなければなりません**（半角に直すと規則の表記が
変わる。過去に casefold を掛けて「ＦＩＡ」が `fia` になった事故があります）。
NFKC を 1 文字ずつ掛けて「正規化後の何文字目が原文の何文字目か」の対応表を
作り、位置を戻しています。`㍿` のように 1 文字が 4 文字に開く場合まで
`tests/test_search.py` で見ています。

#### 原本 PDF の該当ページに直行する（ページはチャンクの先頭ではない）

`pdf_url#page=N` で原本の該当ページが開きます。8,778 チャンクすべてに
1 起点のページ番号が入っていて、ページ数の範囲外は 0 件です。

**ここで最初に出したものは間違っていました（2026-09-11 に修正）。**
チャンクの `page_start`（＝見出しがあるページ）を渡していたのですが、
見出しの検出が効かない規則では 1 つの見出しが 20 ページ分の本文を抱えます。

| | 実測 |
| --- | --- |
| 同一ページに収まるチャンク | 4,549（51%） |
| 2-3 ページ | 1,558（17%） |
| 4-9 ページ | 963（10%） |
| **10 ページ以上** | **1,708（19%）** |

10 ページ以上またぐものは 28 規則に集中しており、最多は FIA 付則J項の
406 件です。実例として、付則J項の「サイドロールバー」（8.2.4）は **P.50**
にあるのに **P.41** と表示し、PDF リンクも P.41 を開いていました。9 ページ
のずれです。

`chunks.pages` に「本文の何文字目からどのページか」の対応表を持たせ、
一致箇所の文字位置（`excerpt.first_match`）から実ページを引くようにしました。

#### 当てにならない条見出しは出さない

同じ理由で、**引き継いだ条見出しは一致箇所の条とは限りません**。上の例では
「3.3) 自動燃料遮断装置すべてのグループについて推奨：」と表示していましたが、
中身は 8.2.4) サイドロールバーの定義です。規則を調べる道具で条を取り違えて
見せるのは、黙っているより悪いと判断しました。

判定は「一致箇所のページが見出しのページから 1 ページ以内か」。外れたときは
**本文から条項を拾い直します**（`excerpt.clause_at`）。変換後の本文には
「8.2.4)　サイドロールバー…」のように目印が残っているので、一致位置から
手前に向かって探せば実際の条が分かります。拾えなければ規則名とページだけを
出します。

誤検出を潰すのに条件を 3 つ足しました（いずれも実データで踏んだもの）。

- **目印の直後に空白を要求する**。無いと「9)のうちの1つ」「第253条4に
  合致しなければ…」のような折り返し行を拾う
- **先頭行は飛ばす**。チャンクの本文は「見出し + 本文」なので、先頭行は
  引き継いだ見出しそのもの。拾うと直したはずの間違いをそのまま出す
- **`" | "` を含む行は外す**。表を平坦化した行で、「031) | オリジナル車両」
  「211) | 主要寸法」を条項と誤認していた

残る限界として、付則J項のように見出しが検出できていない領域では場所を
**ページ番号でしか示せません**（「ラリー ロールバー」では 15 件中 10 件）。
根本は変換側の見出し検出で、そこは未着手です。

AI 回答の根拠一覧も原本ページへ送っていますが、**あちらの条見出しには
まだこの手当てが入っていません**（根拠の本文自体は正しく、ラベルだけの問題）。

制約として、スマホではブラウザが PDF をダウンロード扱いにして
ページ指定が効かないことがあります。現場でスマホから引く用途では
そこは割り切りになります。

#### 図版は「この条の図」と言える範囲だけ

図版 1,423 枚のうち、検索結果に出すのは**該当条文に紐づくものだけ**です
（`build_index.py` の `_clause_figures`）。見出しの構造が薄い規則では
1 チャンクがページをまたいで広がり、40 ページ分の図が全部ぶら下がります。
それは条文と図の対応ではなく単なる図版集なので、**ページ幅 2 ページ以内・
1 条あたり 6 枚まで**で切りました。

実測: 図を持つチャンクは素朴に集めると 1,868 件、そのうち 956 件が
6 ページ以上に広がっていました。絞った結果は **663 件**です。
「ロールケージの最低限の構成（P.29）→ P.29 の図 2 枚」のように、
対応が言える組だけが残ります。構造の薄い規則では図が出ませんが、
出せないときに出さないほうが正しいと判断しました。

## 7. 配信と資産の置き場

- 静的 SPA + API を 1 つの Cloud Run サービスで配信（現構成を踏襲）。
- `content/` は 101MB（図版 58MB / `document.json` 24MB / 生成 HTML 20MB）。
  設計時は「図版は GCS + Cloud CDN に移すのが最終形」と考えていましたが、
  実測の結果**見送りました**（下記）。
- **原本 PDF は git に入れません**（JAF の著作物）。`.cache/pdf/` に留めます。

### 図版の GCS 移設は見送った（2026-09-10）

「図版も埋め込みと同じで git に積み上がる」と考えていましたが、**測ったら
違いました**。

| コミット | 変更ファイル | うち webp |
| --- | --- | --- |
| 143 文書を再変換 | 213 件 | **8 件** |
| 生成 HTML 160 本を作り直し | 161 件 | **0 件** |

**同じ PDF・同じ dpi なら WebP のバイト列まで同一**になるので、git は変更なしと
見ます。図版が新しい blob になるのは JAF が実際に PDF を差し替えたときだけで、
年 20 文書 × 約 10 枚 × 38KB なら**年 8MB 程度**です。埋め込み SQLite が 1 行の
変更で毎回 34MB 積んだのとは性質が違いました（あちらはファイル全体が書き
換わるため）。

実際に効いていたコストは**デプロイのアップロード 121MB**でした。これは
Cloud Build トリガー（`cloudbuild.yaml`）で 0 にできるので、配信経路を触る
必要がありません。

移設を見送るもう一つの理由は、リスクの大きさです。

- 生成 HTML は `assets/...` の**相対パス**。検索エンジン経由の読者が見る
  ページなので、絶対 URL への書き換えを誤ると画像が全滅する
- 図版のファイル名は `fig-p0042-01.webp` で**内容ハッシュを含まない**。
  JAF が差し替えると同じ名前で中身が変わるため、CDN に長期キャッシュを
  効かせると古い図が残る（移設するなら名前を内容ハッシュ付きに変える必要がある）
- 公開バケットは新しい露出面になる
- 1,521 オブジェクトの同期漏れは、公開サイトの画像欠けとして出る

**再検討する条件**: 週次同期のコミットで webp が継続的に数百件動くように
なったとき（= JAF が図版を頻繁に差し替えるようになったとき）。

- **埋め込みキャッシュ（34MB）は GCS に移設済み**です。SQLite のバイナリは
  git の差分圧縮が効かず、1 行増えるだけで毎回まるごと新しい blob が積まれるため、
  図版より先にこちらを移しました。git に残るのはマニフェスト
  `data/embeddings.manifest.json` だけです（[`embeddings-storage.md`](./embeddings-storage.md)）。
  配信経路には関わらないので、公開中のサイトに影響しません。

## 7-b. 年度版のまとめ方と更新履歴

JAF は年度が変わると**別ファイル**として公開します。ファイル名が変わるので
こちらでは新規追加に見え、2026 年版と 2027 年版が同じセクションに並んで
どちらが有効か分からなくなります（2026-09-10 時点で実際に 5 件）。

### 系列キーは PDF のファイル名から取る

タイトルで寄せてはいけません。FIA の「2026年競技規則_日本語版」は
WEC・WRC・WTCR・地域ラリーで**4 本とも同名**で、束ねると別物が混ざります。
ファイル名側は分かれているので、そちらを使います（`jafreg/series.py`）。

```
2026_jaf_sport_reg_race_20260101-801c15  →  jaf_sport_reg_race
jaf_sport_reg_race_20270101-01-9289b7    →  jaf_sport_reg_race
2026_fia_wec_sport_reg_ja_20260101-...   →  fia_wec_sport_reg_ja
2026_fia_wrc_sport_reg_ja_20260113-...   →  fia_wrc_sport_reg_ja   ← 別系列
```

年度の接頭辞・末尾の施行日・連番・ハッシュを剥がします。docId の作り方が
途中で変わっている（新しいものは年度の接頭辞が無く `-01` が付く）ため、
剥がす要素を並べて全部落とします。

### 「JAF が更新した」と「こちらが再変換した」を分ける

これが履歴の正しさの要点です。`data/changes/2026-09-09.json` は 143 件が
`updated` ですが、これはパイプラインを直したことによる再変換で、
`uploadDate` は `previousUploadDate` と同じままです。素朴に差分を履歴にすると
**全規則に「2026-09-09 更新」が付き、JAF が更新したように見えてしまいます**。

判定は `uploadDate` が変わったかで行い、変わっていないものは `reconvert`
として記録するだけで表示しません（`build_history.py`）。実データで
「JAF 更新の記録がある文書 0 件」になることを確認しています。

表示する日付は **JAF の掲載日**です。こちらが検出した日ではありません。

### データの流れ

```
data/state.json  ┐
data/changes/*.json ┴→ build_history.py → data/history.json
                                              ↓
                        build_index.py → search.db の docs.series / edition / history
                                              ↓
                          /api/documents/<docId>/history → 画面
```

| イベント | 意味 | 表示 |
| --- | --- | --- |
| `listed` | JAF に掲載された（その版の初出） | 「JAF に掲載」 |
| `updated` | JAF が掲載日を変えて差し替えた | 「JAF が更新」（太字） |
| `edition` | 同じ系列に別の年度版が公開された | 「2027年版が公開 → 開く」 |
| `removed` | JAF の一覧から消えた | 「JAF の一覧から削除」 |
| `reconvert` | こちらの再変換 | **出さない** |

### 画面

- 規則ページの meta 行に「更新履歴」ボタン。押すと `<dialog>` で日付一覧。
  Esc・背景クリック・フォーカスの閉じ込めはブラウザ任せで自前実装しません。
- 別年度版があれば本文の上に相互リンクのバナーを出します。
- 生成 HTML（`/content/<docId>/index.html`）には履歴を載せていませんでした
  （この HTML そのものを 2026-09-11 に廃止。下の 7-f）。
  変換時に履歴が確定しておらず、載せると毎週 160 本を書き直すことになるためです。

### 追えないこと

- **掲載日を変えずに差し替えられた場合**は検出できません。SHA-256 は見て
  いるので再変換はされますが、JAF の更新としては記録しません
  （掲載日が動いていないので、こちらの都合と区別できない）。
- 週次実行なので、**週の途中に 2 回更新された場合は最後の 1 回**しか残りません。
- 2026-09-09 より前の履歴はありません。それ以前は JAF の掲載日を初出として
  1 行だけ持ちます。

## 7-c. 条単位の改正差分

JAF 自身が出していない機能で、このサービスの一番の売りになり得ます。

### 比較の相手は 2 種類

| 種別 | 相手 | いつ取れるか |
| --- | --- | --- |
| `edition` | 同じ系列の前年度版 | **いますぐ**。JAF は年度版を別ファイルで公開するので両方が手元にある |
| `revision` | 同じ規則の前の版（`content/<docId>/previous.json`） | 次に JAF が掲載日を変えて差し替えたとき |

`revision` のために、`cli.py sync` が上書き前に `document.json` を
`previous.json` へ退避します。**再変換（掲載日が同じ）では退避しません**。
前の版として残すべきものは JAF が変えた版だけで、こちらの都合で作り直した
ものではないからです。

### 突き合わせの鍵でつまずいた点

鍵は「条項番号の連なり」ですが、**レベル 1（文書タイトル）は除きます**。
タイトルには年度が入っており（`clause` が `２０２6` / `２０２7`）、鍵に
含めると **50 条すべてが「消えた／増えた」になります**（実測）。

条番号がずれる改正（条の挿入で以降が繰り下がる）を全条書き換えとして
出さないよう、番号で対応が付かなかったものは見出しの文字列の近さ
（0.72 以上）で救済します。

### 「軽微」を類似度で決めてはいけない

最初は類似度 0.95 以上を「軽微」としていました。**これは誤りでした。**
走行距離が「30km → 20分」に変わった条が類似度 0.971 で「軽微」に
分類されました。長い条文の中の 1 か所の数値変更は類似度が高く出るため、
規則の実質的な変更を「軽微」と呼んでしまいます。

判定は「**年号を伏せたら同一になるか**」という厳密な条件に変えました
（`year_only`）。年度版の読み替えだけを正確に切り分けられます。
このラベルが付いても差分の行は必ず表示します。既定では畳まず、
利用者がチェックボックスで隠せるようにしてあります。

### 実データでの結果（5 組すべて）

| 系列 | 条項 | 対応 | 変更 | 年号のみ | 追加 | 削除 |
| --- | --- | --- | --- | --- | --- | --- |
| 日本レース選手権規定 | 50 → 50 | 100% | 7 | 5 | 0 | 0 |
| 日本サーキットトライアル選手権規定 | 47 → 47 | 100% | 1 | 3 | 0 | 0 |
| 自動車競技の組織に関する規定 | 20 → 20 | 100% | 3 | 0 | 0 | 0 |
| JAFカップオールジャパンサーキットトライアル規定 | 25 → 27 | 93% | 4 | 2 | 2 | 0 |
| 日本カート選手権規定 | 87 → 78 | 97% | 29 | 1 | 2 | 11 |

カートの「削除 11 条」は突き合わせ失敗ではなく、JAF が部門の個別列挙を
「第 3 条に定める部門」への参照に組み替えた実際の再構成です（目視確認済み）。

### JAF の公示を巡回して紐づける

公示一覧は **JSON API** から取ります。一覧ページは JS で描画されるため
HTML を読んでも項目が入っていません（実測）。

```
/api/announcements/getlist?db=0&language=ja-JP&page=N&limit=50
  &searchItemID={EBE790C2-6FEB-421E-BF30-B9EE5C14C7C0}
```

`searchItemID` は必須で、省くと 500 が返ります。DOM 非依存なので見た目の
変更には強い一方、API の形が変われば壊れます。総件数 0 で止めるガードを
入れてあります。詳細ページはサーバ描画ですが、クラス名に依存すると壊れる
ので **公示 No. は正規表現、添付は `main` 配下の `a[href$=.pdf]`** という
素朴な取り方にしています。

**突き合わせは添付の文言を優先します。** 2025-03-31 の公示
（No.2025-WEB025）は 1 件で **20 本の新旧対照表**を抱えており、タイトル
（「新システム稼働に伴う国内競技規則細則等の一部改正について」）だけでは
個々の規則に結びつけられません。添付側を見れば
「自動車競技の組織に関する規定_一部改正（新旧対照表）」と分かります。

規則名は最長一致で採ります。「自動車競技に関する申請・登録等手数料規定」と
「カート競技に関する申請・登録等手数料規定」のように似た名前が並ぶため、
短い側に引き寄せられると取り違えます（実データで両者が正しく分離される
ことを確認済み）。

実データ（2024-01 以降 439 件 / 規則変更 107 件）での結果:

| | 件数 |
| --- | --- |
| 紐づいた系列 | 55 |
| 対比表つきの紐づけ | 36 |
| 紐づかなかった公示 | 16 |

**誤紐づけは 0 件**でした。未紐づけ 16 件はコーパスに無い規則
（地方選手権のクラス区分、ジュニアカート選手権統一規則など）か、
表記が大きく違うもの（我々が「第1編第4章…規定される」、公示が
「第1編第3章…基づく」）です。誤リンクより取りこぼしを選ぶ設計です。

### CI に紐づけステップが無かった（2026-09-11 に発覚）

**「公示一覧を巡回」で `announcements.json` は毎回更新されるのに、
`link_announcements.py` を走らせていませんでした。** ワークフローに
ステップが最初から無く、紐づけは手元で流したときだけ更新されていました。

手動同期で公示が **439 → 1,188 件**（2016 年まで遡れた。`id` と `url` は
全件ユニークで重複なし）に増えたのに、`announcement_links.json` が
コミットに現れないことで気づきました。作り直した差は小さくありません。

| | 前 | 後 |
| --- | --- | --- |
| 紐づいた系列 | 55 | **63** |
| 対比表つき | 36 | **60** |
| 公示が紐づいた規則（`docsWith.announcements`） | 60 | **68** |
| 未紐づけ | 16 | 98（古い公示が増えたぶん。carry していない年度版向け） |

対比表は JAF 自身の新旧対照 PDF で、改正を追うときに一番効く資料です。
それが 36 → 60 件に増えました。ワークフローに
「公示を規則に紐づける」ステップを追加しています。

**教訓**: 入力（`announcements.json`）を更新するステップと、それを使う
派生物（`announcement_links.json`）を作るステップは、必ず並べて置くこと。
`git add -A content data` は変更があれば拾うので、**生成していないことには
気づけません**。

### JAF の公示による検証

JAF は <https://motorsports.jaf.or.jp/regulations/announcement> で公示を
出しており、これが差分の**正解データ**になります。ただし 2 種類あって
性質が違います。

**対比表が付くかは公示ごとに違います。**「制定」だから無い、とは限りません。

| | 実データ（2024-01 以降） |
| --- | --- |
| 規則変更の公示 | 107 件 |
| うち対比表（新旧対照表）がある | 17 件 |

「一部改正」に多い一方、「制定」でも付くことがあります（2027 年
日本ドリフト選手権規定の制定など）。逆に日本レース選手権規定 2027 年版の
制定公示は本体 PDF だけで変更点の列挙がありませんでした。
つまり **公示の種別ではなく対比表の有無で分岐する**のが正しい設計です。

対比表がある規則では、差分ページの冒頭で JAF の対比表へ案内します
（自動差分より確実なので、そちらを先に見てもらう）。対比表が無い改正を
埋めるのが我々の自動差分という位置づけです。

**実施した検証**（公示 No.2026-WEB077 / 2026-09-02 / 自動車競技に関する
申請・登録等手数料規定 対比表）:

| 対比表の「改正前」 | 我々の変換結果 |
| --- | --- |
| 第17条 抗議料 国際 106,700（97,000＋9,700） | ✓ 一致 |
| 第17条 抗議料 国内 53,300（48,455＋4,845） | ✓ 一致 |
| 第17条 抗議料 準国内・地方・クローズド 21,200（19,273＋1,927） | ✓ 一致 |
| 第18条 控訴料 国際 266,900 / 国内・準国内 160,200 / 地方・クローズド 106,700 | ✓ 一致 |
| 第18条 中央審査委員会 534,000 | ✓ 一致 |

**13 項目すべて一致**。表の構造（格式／金額／内訳）も保たれています。
改正後の金額（120,000 など）は含まれておらず、この版が改正前のものである
ことも確認できました。

> 照合するときは **NFKC 正規化を忘れないこと**。原本は全角数字
> （`１０６,７００`）なので、半角で検索すると 1 件も当たらず「変換が
> 欠落している」と誤診します（実際に一度そう読み違えました）。

**もう 1 件、条項レベルで一致した検証**（公示 No.2026-WEB034 / 2026-04-20 /
自動車競技の組織に関する規定の一部改正）:

| JAF が改正としたもの | 我々の差分 |
| --- | --- |
| 第2条 準加盟クラブの要件 | ✓ 検出（7名以上 → 5名以上） |
| 第9条 本規定の施行 | ✓ 検出（2025年4月1日 → 2027年1月1日） |
| （改正対象ではない） | 前文の改正履歴に 1 行追加 |

**JAF が挙げた 2 条を 2/2 で検出**し、余分な条を誤検出していません。
前文は改正のたびに履歴行が増えるので、差分として出るのが正しい挙動です。

> **PDF の要約読み取りを正解データにしてはいけません。**
> この検証中、公示 PDF の要約が「5名以上 → 7名以上」と**逆の向き**を
> 返してきました。同じ要約は施行日の改正前も「2022年4月1日」と誤って
> 返していました。原本 PDF 2 本を直接読んで
> （2025年版=7名 / 2027年版=5名）我々の向きが正しいと確定しました。
> 照合するときは条文そのものを取り出すこと。

**次の検証**: JAF が手数料規定の PDF を差し替えたら、我々の差分は
**第17条・第18条だけ**を変更として挙げるはずです。現時点の一覧の
アップロード日は 2026-03-23 のままで、まだ差し替わっていません。

### 公示日と一覧のアップロード日はずれる

日本レース選手権規定の 2027 年版は **公示が 2026-08-04**、一覧の
アップロード日は **2026-09-09** でした。公示のほうが約 1 か月早いので、
公示一覧を巡回することで更新をより早く検知できます（実装済み）。

### データの流れ

```
content/<docId>/document.json ┐
content/<docId>/previous.json ┼→ build_diffs.py → content/<docId>/diff-<base>.json（本体）
data/history.json（系列）      ┘                 → data/diffs.json（一覧）
                                                        ↓
                                    build_index.py → docs.diffs
                                                        ↓
                        /api/documents/<docId>/diff/<baseDocId> → /diff/<docId>/<base>
```

本体を `content/` に置くのは、Docker の build context に `content/` が
そのまま入るためです（`data/*` は除外設定なので通したいものを個別に書く）。

> **`data/` から通すファイル名は build_index.py の既定値と必ず揃えること。**
> `data/announcement_links.json` を `data/announcements.json` と書き間違えて、
> 公示が**黙って 0 件**のまま公開してしまいました。任意入力は無くても動くので
> エラーになりません。いまは (1) `build_index.py` がビルドログに入力の有無を
> 出す、(2) `/api/healthz` の `docsWith` に件数を出す、の 2 つで気づけるように
> してあります。デプロイ後は `docsWith` を必ず見てください。
算出はビルド時に済ませます。数百ページの規則をサーバ側で `difflib` に
かけると待たされるためです。

### 差分ページに必ず出している注意書き

条項番号で突き合わせた自動生成の結果であり、JAF による正式な改正の告知では
ないこと、自動変換の誤りが差分として現れうることを明記しています。

## 7-e. 検索エンジン対策（SEO）

「検索にヒットさせたい」という要求への対応（2026-09-10）。

> **現在この機能は切ってあります（2026-09-10）。** 同日、JAF のサイト
> ポリシーに資料の再配布を認めない旨の明示があることが分かったため、
> オーナーの判断で検索露出を停止しました。仕組みは全部そのまま残して
> あり、再開はスイッチ 1 か所です。下の「検索露出のスイッチ」と 9 章を
> 参照してください。

### 実測した出発点

順位を上げる話の前に、**そもそもインデックスされていなかった**。

| 項目 | 状態 |
| --- | --- |
| `sitemap.xml` | 無し |
| `robots.txt` | 無し（404） |
| `canonical` | 無し |
| `/doc/<docId>` の HTML | 160 件すべて**同一**（`dist/index.html` の JS シェル。`<title>` も `description` も同じ） |
| トップから規則へのリンク | JS を実行しないと **0 本**（一覧は `/api/documents` を取ってから描いている） |
| 同じ本文の URL | `/doc/<docId>`（JS 描画）と `/content/<docId>/index.html`（全文入り）の 2 系統 |

Googlebot は JS を実行するが、レンダリングは待ち行列で後回しになる。
5,100 ページ超の全文をそれ任せにするのは博打で、しかも 160 件が同じ
`<title>` では出発点にもならない。

### 寄せ先は `/doc/<docId>` にした

同じ本文が 2 つの URL に出ているので、どちらかを正本に決める必要がある。
**アプリ側（`/doc/<docId>`）を canonical にした**。検索から来た読者が
着地したときに、全文検索と AI 質問が付いているのはこちらだから。

> **以下は 2026-09-10 時点の記録です。** 翌日に全文の配信そのものを
> やめたため、`/content/<docId>/index.html` と本文プリレンダは存在しません
> （下の 7-f）。当時の判断の経緯として残します。

`/content/<docId>/index.html` は **noindex にしない**。JS 無しで全文が
読める唯一の経路として残し、`canonical` で `/doc/<docId>` に寄せる
（`jafreg/render.py`）。あわせて「検索と AI 質問つきのビューアで開く」
リンクを注意書きの中に入れ、内部リンクとしても効かせている。

### やったこと（`server/seo.py`）

- **`/doc/<docId>` の head を規則ごとに差し替える** — `title`（NFKC を
  かけて全角を半角に寄せ、末尾の `_20260101` は落とす）、`description`、
  `canonical`、OG、JSON-LD（`WebPage` + `BreadcrumbList` + `citation`）。
- **`description` は条見出しを並べる** — 既定文の使い回しでは 160 件が
  同じ説明文になる。`第1条 目的／第2条 …` と並べておくと、「第12条
  安全ベルト」のような検索で、どの規則のどこに何があるかが SERP の
  時点で分かる。
- **本文をサーバ側で同梱する** — 変換時に作った
  `content/<docId>/index.html` から `<article>` を切り出し、`#prerender`
  として `#root` の後ろに置く。React は `#root` しか触らないので競合せず、
  SPA 起動時に `index.tsx` が `#prerender` を消す。図版の `src="assets/…"`
  は `/doc/…` から解けないので絶対パスに書き換える。
- **トップに全 160 件の素の `<a>` を置く** — sitemap で URL は伝わるが、
  内部リンクが 1 本も無いページは「どこからも参照されていない」扱いに
  なる。ここも `#prerender`。
- **`/search` `/ask` は noindex + `robots.txt` で Disallow** — クエリ違いで
  URL が無限に増える種類のページ。クロール予算を使わせない。
- **gzip を有効にした** — プリレンダで `/doc/` の HTML が数十〜250KB に
  なる。`/api/ask`（SSE）だけは素通しにする。Starlette の
  `GZipMiddleware` はストリーミング応答をチャンクごとに握るため、
  かけると回答のトークンが手元に溜まって流れない。
- **`sitemap.xml` / `robots.txt`** — `docs` テーブルから作る（トップ +
  規則 160 + 改正差分。`lastmod` は JAF の掲載日）。`SITE_ORIGIN` 環境
  変数で origin を差し替えられるが、既定は独自ドメイン。Cloud Run の
  `*.run.app` にも同じ中身が出るので、寄せ先を固定しないと評価が割れる。

### プリレンダの切り詰めで踏んだこと

上限（250KB）を超える規則は途中で切る。最初は「最後の `</p>` まで戻す」
実装にしたが、770 ページの WEC 規則では**目次（`<nav><ol>…`）そのものが
上限より長く**、目次の途中で切ろうとすると直前の `</p>` まで戻ってしまい、
本文が 1KB も入らなかった（3.2MB → 1,288 バイト）。

タグを数えて切り、開いたままのタグをこちらで閉じる方式に変えた
（`seo._truncate_html`）。`tests/test_seo.py` にこのケースを入れてある。

### 確認方法

`/api/healthz` に `seo` を足した。`sitemapUrls` が 1（トップだけ）なら
`docs` テーブルを読めていない＝規則の URL がクローラに一切届かない。

```json
"seo": {"origin": "https://jp.motorsports-regulations.org", "sitemapUrls": 166}
```

Cloud Build の「中身を確認」ステップで、`sitemapUrls >= 100` と、
規則ページ 1 件に `canonical` / `description` / `#prerender` /
JSON-LD が入っていることを実物で確かめて落とすようにした。ここが
素の JS シェルに戻ると、検索には二度と出なくなる。

### 検索露出のスイッチ

露出のオン／オフは **`server/seo.py` の `SEARCH_INDEXING` 1 か所**で決まります。
`False`（現在の値）のとき:

| | 挙動 |
| --- | --- |
| `robots.txt` | `User-agent: *` / `Disallow: /` のみ。**Sitemap 行は出さない**（全面禁止と併記すると言っていることが食い違う） |
| HTML の `<head>` | `<meta name="robots" content="noindex,nofollow">` が入る |
| すべての応答 | `X-Robots-Tag: noindex, nofollow`（`server/app._NoIndexHeader`）。`/content/<docId>/index.html` と図版にも掛かる |
| `sitemap.xml` | **作り続ける**（配信もする）。robots.txt から案内しないだけ |
| head のタグ・本文プリレンダ | **そのまま残す**。再開時に出し直す必要がない |

`X-Robots-Tag` は ASGI 層でヘッダだけ触る実装にしています。
`@app.middleware("http")`（`BaseHTTPMiddleware`）はストリーミング応答を
握るため、`/api/ask` の SSE が流れなくなります。

再開するときは `SEARCH_INDEXING = True` に戻して出すだけです。Cloud Build の
「中身を確認」ステップが `robots.txt` とページの `<meta>` を突き合わせるので、
「robots は禁止なのにページは canonical だけ」という中途半端な状態では
ビルドが落ちます。

**注意**: `Disallow` でクロールを止めている間、クローラは `noindex` を
読めません。すでにインデックスされた URL は URL だけ残ることがあります。
今回は事実上インデックスされていない状態から止めたので影響はほぼ無い
見込みですが、取り除きたい URL が出てきた場合は Search Console の削除
ツールを使うか、いったんクロールを許して `noindex` を読ませてください
（この 2 つは同時にはできません）。

#### 作り替えるときの見通し

- `/api/documents/<docId>` は **メタデータ + 目次（`toc`）だけ**返す。`blocks`
  （本文）を返さない。目次の各見出しには原本のページを持たせ、
  `pdf_url#page=N` で送る
- `/content` のマウントは**図版（`assets/`）だけ**に絞る。`document.json` と
  `index.html` は配らない
- `content/*/index.html`（16.7 MB）は**生成をやめて消せる**。`render.py` と
  `rerender.py` も不要になる。`document.json` は検索インデックスの元なので
  リポジトリには残すが、**配信はしない**
- 図版 58 MB は残す（検索結果で条に紐づくものを出しているため）
- 全文はサーバ側に残る（`search.db` のチャンク本文が抜粋の元）。
  **索引に持つことと公開配信することは別**、というのがこの設計の要点です
- 差分ページ（`/diff/...`）は新旧の条文を並べるので、抜粋の範囲に収めるか
  どうかを別に決める必要があります

#### OGP: 共通カード 1 枚にした（2026-09-11）

`og:type` / `og:site_name` / `og:locale` / `og:title` / `og:description` /
`og:url` / `og:image` を規則ごとに出しています（`server/seo.py` の `_common`）。
`twitter:card` は `summary_large_image`。

**画像は全規則で共通の 1 枚**（`public/og-card.png`、1200×630、
`pipeline/build_icons.py` の `og_card`）。規則ごとに 160 枚作る案は採りません。

**判断の理由**: Slack・LINE・X は `og:title` と `og:description` を画像の横に
**テキストで**出します。規則名はすでにそこに出ているので、画像にもう一度
焼き込むのは重複です。そのために週次同期で 160 枚を作り直す手間は
釣り合いません。オーナーの言い方では「規則を共有したとして、人間そこまで
見てるかなあ？」。

カードの文言に**件数を入れていません**（160 規則、5,148 ページ）。規則が
増えたときに画像だけ古くなるのを避けるためです。

**robots.txt が全面 Disallow の間はカードが出ません。** リンク展開の
クローラ（Twitterbot、Slackbot など）は robots.txt に従います。画像とタグは
入れてありますが、実際に出るのは `SEARCH_INDEXING = True` にしてからです。

フォントについて: OG カードは日本語を描くので CJK フォントが必要です。
連携先の Linux VM と手元の mac の両方で見つかるよう候補を並べ、**無い太さは
近いものに落とします**（実測: 連携先の VM には NotoSansCJK の Bold と
Regular しか無く、Medium が無い）。

### 変えたもの

- **`/api/documents/<docId>`** — `document.json` をそのまま返すのをやめ、
  メタデータ + 目次（`docs.toc`）だけにした。見出しごとに原本のページを持つ。

  見出しが検出できず、規則内検索と原本リンクで案内する）
- **`/content`** — `StaticFiles` のマウントをやめ、**図版だけ**を配る

- **規則ページ**（`DocumentView`）— 全文表示から次の形に。
  1. 注意書き（本文を載せていない理由とサイトポリシーへのリンク）
  2. 原本 PDF を開く導線
  3. **この規則の中を検索**（`/api/search?doc=<docId>`。抜粋・図版・

  4. **条文の一覧**（見出し → `pdfUrl#page=N`。既定は条・章まで、

  5. 更新履歴・年度版・公示
- **改正差分** — 条見出しのリンク先をアプリ内アンカーから原本 PDF の

  `pdfUrl` を添えている
- **SEO の本文プリレンダを仕組みごと削除**した。露出を再開したときに
  本文が初回 HTML に戻らないようにするため。トップの一覧（`#prerender`）は
  残す
- `description` の「〜の全文」を「〜の条文一覧」に直した。載せていないものを
  検索結果に書かない

| --- | --- | --- |

### ビルドで確かめていること

Cloud Build の「中身を確認」に足しました。**ここが開くと、サイトポリシーと

### 残っている判断

- `document.json`（21.9 MB）はイメージに残っています。配信経路は無いので
  読めませんが、多段ビルドで最終イメージから落とすこともできます

## 10. 実 PDF での検証結果（2026-09-09）

`samples/` に置いた 4 本で変換を実行しました。

| 文書 | ページ | 本文 | 段落 | 見出し | 図版 | 表 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| ラリー競技に参加するクルーの装備品に関する細則 (2025) | 2 | 1,289字 | 23 | 4 | 2 | 1 |
| 第2編 ラリー車両規定 (2026) | 43 | 53,218字 | 802 | 266 | 34 | 0 |
| レース競技に参加するドライバーの装備品に関する細則 (2026) | 13 | 6,744字 | 122 | 11 | 11 | 10 |
| ラリー/スピード競技における安全ベルトに関する指導要綱 (2027) | 5 | 2,281字 | 57 | 20 | 13 | 2 |

本文・図版・表とも原本と突き合わせて一致を確認しました。とくに、
ベクタ図（ロールケージの断面図、HANS の取付角度図など）が
①②③④ の引き出し番号や「70mm以下」といった寸法注記ごと
1 枚の画像として本文の正しい位置に入ることを確認しています。

### 検証で見つけて直した問題

1. **1 行 = 1 段落になっていた**
   JAF の PDF は行ごとにテキストブロックが切られている。そのままだと
   1 行ごとに `<p>` が並んで読めず、RAG のチャンクも文の途中で切れる。
   「直前の行が右マージンまで達している／行送りが妥当／行頭に全角字下げも
   項番も無い」ときに繋ぎ直す処理を入れた。ぶら下げインデント（項番の幅だけ
   右にずれた継続行）も追随する。平均段落長が 43 字 → 61 字に改善。

2. **枠囲みの本文が画像になり、テキストから消えていた**  ← 影響大
   `［参考］ 国際モータースポーツ競技規則付則Ｌ項（抜粋）` のような
   罫線で囲んだ本文が、罫線をベクタ図と見なして丸ごと画像化されていた。
   その中の条文が全文検索にも AI の根拠にも出てこない状態だった。
   「枠内が文字で埋まっており、描画パスが枠線程度しか無い」領域は本文として
   扱うようにした（`is_framed_text`）。
   これだけでレース装備品細則の抽出文字数が **5,051 → 6,744 字（+34%）** に増えた。

3. **ヘッダ（柱）が章ごとに変わると除去できなかった**
   「第１章　一般規定」のような柱は章が変わると文字列も変わるため、
   出現ページ数の下限を全ページの半数ではなく 4 ページで頭打ちにした。
   本文より小さいフォントであることを別途要求しているので、
   本物の見出しを巻き込む危険は小さい。

4. 併せて、扉ページを誤って OCR 対象にする誤検知（文字数だけで判定していた）と、
   見出し行のない表の 1 行目が太字になる問題も修正した。

### 残っている改善余地

- `第 1 条` のように原本で字間が空いている見出しは、そのまま目次に出る。表示時に正規化したい。
- `9.4）…` のように項番から条文本体が続く行は見出しにせず本文に落としているが、
  項番は `clause` として各ブロックに保持しているので、AI 回答の出典表記には使える。
- 図版のサイズ実測: 43ページ・図34枚で約 1.1MB。JAF 全体（推定 8,000 ページ規模）では
  100〜200MB になる見込み。git でも当面は回るが、GCS 移設の判断材料になる。
