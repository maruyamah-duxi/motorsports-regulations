# JAF モータースポーツ諸規則アプリ 再設計メモ

対象: <https://jp.motorsports-regulations.org/>（GCP Cloud Run / project `gen-lang-client-0036162343` / us-west1）
リポジトリ: `maruyamah-duxi/motorsports-regulations`

---

## 1. 現状の何が問題だったか

AI Studio が生成した初版は **静的な React アプリに規則本文をベタ書き** した構成でした。

| 症状 | 直接の原因 |
| --- | --- |
| JAF の更新に追いつけない | `data_part1.ts` / `data_part2.ts` に本文が手書きで埋め込まれている。JAF 側が PDF を差し替えても何も起きない。取り込まれているのは **5 件のみ**（JAF の配布は国内 125 件 + 国際 35 件）。 |
| PDF 全文がテキスト化できていない | 変換工程が存在せず、LLM に要約させた文章が貼られている。原本との一致が保証されない。 |
| 画像が PDF と同じように出せない | 画像抽出そのものが無い。加えて、JAF の車両規則の図は大半が **ベクタ描画** なので、一般的な「埋め込み画像を取り出す」方式（`get_images()` 等）では 1 枚も取れない。 |

つまり **データ生成パイプラインが無い** ことが根本原因で、UI をいくら直しても解決しません。
そこで「PDF → 構造化データ」を作る工程を新設し、アプリはその生成物を読むだけにします。

## 2. 全体アーキテクチャ

```

motorsports.jaf.or.jp   │  1. crawl    諸規則ページを解析 → catalog.json          │
  /regulations/…  ──────▶  2. diff     アップロード日 + SHA-256 で差分判定        │
  （国内 / 国際）        │  3. convert  変更分だけ PDF → document.json + 図版     │
                        │  4. index    index.json / 検索インデックス / 埋め込み   │
                        │  5. commit   生成物を git に、図版は GCS へ            │
                        └───────────────────────┬────────────────────────────────┘
                                                │
                        ┌───────────────────────▼────────────────────────────────┐
                        │ Cloud Run (既存)                                        │
                        │  ├ 静的配信 (React SPA)                                 │
                        │  ├ /api/search  … SQLite FTS5 (trigram) 全文検索        │
                        │  └ /api/ask     … RAG。規則本文を根拠に引用付きで回答   │
                        └─────────────────────────────────────────────────────────┘
                                     ▲                        ▲
                              GCS: 図版・原本 PDF 保管    Gemini API（鍵はサーバ側のみ）
```

原則:

- **生成物は決定的**。同じ PDF からは同じ JSON が出る（`pipelineVersion` で世代管理）。
- **アプリは変換結果を読むだけ**。UI の改修とデータ品質の改善を分離する。
- **原本 PDF は git に入れない**。JAF の著作物なのでキャッシュは CI の一時領域と GCS に留め、リポジトリには変換結果とメタデータのみ置く。

## 3. 更新追従（課題①）

### 実測した制約

JAF の PDF レスポンスは以下でした（2026-09-09 実測）:

```
cache-control: no-cache, no-store
content-type: application/pdf
（ETag なし / Last-Modified なし）
robots.txt: 404
```

**条件付き GET が使えません。** よって次の 2 段構えにします。

1. **一覧ページの「アップロード日」** — `p._date` に `アップロード日：2026年9月9日` が入っている。
   ここが変わったものを第一候補にする。
   さらに「最近のアップデート」タブは全件をアップロード日の降順に並べた実質の更新フィードなので、
   カテゴリ一覧と突き合わせれば取りこぼしを検出できる。
2. **本体の SHA-256** — 日付据え置きでの差し替えを拾う。ダウンロードは避けられないので、
   1.5 秒間隔・連絡先入り UA で夜間に静かに巡回する。

### 差分の見せ方

`data/changes/YYYY-MM-DD.json` に「追加 / 更新 / 削除 / 失敗」を残し、
コミットメッセージと GitHub の Job Summary に反映します。
将来的に、更新前後の `document.json` を条単位で突き合わせれば
**「第◯条のここが変わった」という改正差分ページ** が作れます。
これは JAF 自身が提供していない機能で、このサービスの一番の売りになり得ます。

### JAF サイトの DOM（クローラが依存している構造）

```
div.tab-menu
 ├ ul._header > li.js-slideTab-header        「カテゴリ一覧」「最近のアップデート」
 └ div._content.js-slideTab-body [0]         ← カテゴリ一覧
    └ div#01 … div#05                        大分類（h2.heading-primary）
       └ div.togglegroup > div.toggle-accordion
          ├ div._header                      中分類
          └ div._content > ul.list-type-iconBlock > li > a[href$=".pdf"]
                                             p._title / p._date
```

Sitecore 由来の安定した構造ですが、リニューアルで壊れる可能性はあります。
**取得件数が前回比で 3 割以上減ったら異常として落とす** ガードを CI に入れておくのが安全です。

## 4. PDF → HTML 変換（課題②・③）

`pipeline/jafreg/layout.py` が中核です。

### 4.1 本文の抽出と読み順

- PyMuPDF の `get_text("dict")` でブロック / 行 / スパンを取得（bbox・フォント・サイズ付き）。
- **XY-Cut** を再帰適用して段組と読み順を復元。1 段組でも 2 段組でも同じコードで通る。
- **ヘッダ・フッタ除去** は位置だけで判定しない。天地 12% の帯にあり、かつ
  数字を伏せた文字列が全ページの半数以上で繰り返され、かつ本文サイズ以下のものだけを落とす。
  （位置だけで切ると、ページ先頭に来た「第◯章」を巻き添えにする。実際に試作中に踏んだ。）
- **見出し** は「第◯編 / 第◯章 / 第◯条 / 1-1 / 附則 / 別表」等の採番パターンを第一優先、
  フォントサイズ比を第二優先で判定。見出しには安定したアンカー ID を振り、
  **AI 回答や検索結果から条単位で直リンク** できるようにする。

### 4.2 図版（ここが肝）

「埋め込み画像を取り出す」発想を捨てて、**図版が占める領域を決めてページごと切り出す** 方式にしました。

1. ラスタ画像の配置矩形（`page.get_image_info()`）
2. ベクタ描画のクラスタ矩形（`page.cluster_drawings()`）
3. 1 と 2 を近接マージして「図版領域」を確定
4. 罫線・下線（辺が 24pt 未満）、ページ枠（面積比 92% 超）、表として検出済みの領域を除外
5. 残った領域を `page.get_pixmap(clip=…)` で 200dpi ラスタライズ → WebP

この方式なら、線画・寸法線・図中の注記文字がまとめて 1 枚に収まり、**PDF と同じ見た目** になります。
ベクタ図しか無い車両規則でも図が取れるのはこのためです。

### 4.3 図と本文の対応付け

- 図版領域を **1 つのブロックとして本文ブロックと同じ読み順ソートに混ぜる**。
  これだけで「図が本文の正しい位置に入る」が成立します。
- 図版領域の内側に落ちた文字ブロックは本文から除外（図に描き込まれた文字の二重出力を防ぐ）。
- 直前・直後 60pt 以内にある `図◯` `表◯` `写真` で始まる行をキャプションとして図に結びつける。
- 各ブロックに `page` と `bbox` を残すので、後から
  「この段落は原本 P.42 のここ」というハイライト表示や原本ページ並置ができます。

### 4.4 表

`page.find_tables()` でセル配列として取り、HTML の `<table>` にします。
検出に失敗した表は 4.2 の図版扱いに落ちるので、**最悪でも画像として本文の正しい位置に残ります**。

### 4.5 テキスト層が無い / 文字化けする PDF

- ページの抽出文字数と「文字化け率」（U+FFFD・私用領域の比率）を測り、
  閾値を超えたら `warnings` に記録し、HTML 上部に「原本を確認してください」の注意を出す。
- `--ocr` で tesseract（`jpn` + `jpn-vert`）による OCR フォールバックに切り替え。
- 古い年式の PDF（2012 年頃）はスキャン由来の可能性があるため、初回同期のログで要確認。

## 5. データモデル

```
data/
  catalog.json          JAF ページから拾った配布物一覧（毎回上書き）
  state.json            docId → sha256 / uploadDate / 変換統計（差分判定の基準）
  index.json            フロントが最初に読む軽量インデックス（目次 40 件まで）
  changes/YYYY-MM-DD.json  その日の差分
content/<docId>/
  document.json         構造化本文（ブロック配列 + 目次）
  index.html            単体で読める静的 HTML
  assets/fig-pNNNN-MM.webp
```

`docId` は PDF URL のファイル名 + パスの SHA-1 先頭 6 桁。
JAF は改訂時にファイル名を変える（例: `…_20250101.pdf` → `…_20270101.pdf`）ため、
**同一規則の年度違いは別 docId** になります。年度をまたぐ紐付けは
タイトルから年月日サフィックスを除いた「系列キー」を別に持たせるのが良いです（今後の課題）。

`document.json` のブロック:

```jsonc
{ "type": "heading",   "level": 4, "text": "第12条 安全ベルト", "id": "第12条-安全ベルト", "page": 42, "bbox": [...] }
{ "type": "paragraph", "text": "…",                             "page": 42, "bbox": [...] }
{ "type": "figure",    "asset": "assets/fig-p0042-01.webp", "caption": "図3 取付角度", "page": 42, "bbox": [...] }
{ "type": "table",     "rows": [["項目","値"], …],              "page": 43, "bbox": [...] }
```

## 6. 検索と AI Q&A

### 検索

日本語全文検索をクライアント側で持つと、160 本 × 数百ページではインデックスが重すぎます。
Cloud Run 上に **SQLite FTS5 + trigram トークナイザ** の DB をイメージに焼き込む方式を推奨します。

- 外部サービス不要・追加費用ゼロ・数十 ms で返る
- 分かち書き不要（trigram なので「安全ベルト」でも「全ベル」でも当たる）
- ビルド時に `content/*/document.json` から生成するだけ

### AI Q&A（RAG）

現状の実装は**規則のタイトルと要約だけ**を system prompt に流し込んでいるため、
条文の中身を答えられません。RAG に置き換えます。

1. `document.json` を **条（見出し）単位**でチャンク化。メタデータに規則名・条番号・ページ・アンカーを持たせる。
2. Gemini の埋め込みでベクトル化し、FTS5 と同じ SQLite に格納（`sqlite-vec`）。
3. 質問 → ハイブリッド検索（全文 + ベクトル）→ 上位チャンクを根拠として渡す。
4. 回答には **必ず「規則名 第◯条（P.◯）」の出典を付け、HTML アンカーと原本 PDF の両方にリンク**。
5. 根拠が見つからないときは「該当なし」と答えさせる（規則の質問で作話は致命的）。

> セキュリティ注記: 現行リポジトリの `vite.config.ts` は `process.env.API_KEY` を
> **クライアントバンドルに埋め込む** 設定です。デプロイ済みの Cloud Run 版は
> AI Studio が用意した `/api-proxy` 経由でプレースホルダに置き換わっていたため
> 現時点で鍵は露出していませんが、自前でビルドし直すと露出します。
> RAG 化に合わせて **Gemini 呼び出しは必ずサーバ側**に移してください。

## 7. 配信と資産の置き場

- 静的 SPA + API を 1 つの Cloud Run サービスで配信（現構成を踏襲）。
- `content/` のテキストは git で問題ありませんが、**図版 WebP は数千枚・数百 MB 規模**になり得ます。
  git に積み続けると重くなるので、図版と原本 PDF のキャッシュは **GCS バケット + Cloud CDN** に置き、
  git には `document.json` とメタデータのみを残すのが最終形です。
  （試作段階では git に入れて様子を見て、実測サイズを見てから移す。）

## 9. 運用・法務上の注意

- JAF の諸規則は JAF の著作物です。全文を再配信する形になるため、**JAF への事前の照会**を強く推奨します。
  少なくとも、出典表示・原本 PDF への明示リンク・「正式な効力を持つのは JAF 原本」という免責は必須です。
- 自動変換である以上、誤りは残ります。**競技での判断は原本を参照** と各ページに明記してください。
- 巡回は 1 リクエスト 1.5 秒間隔、深夜 1 回のみ。UA に連絡先 URL を含めています。
  `robots.txt` は現在 404（明示的な禁止なし）ですが、設置された場合は必ず従うようにしてください。
- AI の回答は参考情報であり、根拠条文へのリンクを伴わない回答は出さない設計にしてください。

## 10. 実 PDF での検証結果（2026-09-09）

`samples/` に置いた 4 本で変換を実行しました。

| 文書 | ページ | 本文 | 段落 | 見出し | 図版 | 表 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| ラリー競技に参加するクルーの装備品に関する細則 (2025) | 2 | 1,289字 | 23 | 4 | 2 | 1 |
| 第2編 ラリー車両規定 (2026) | 43 | 53,218字 | 802 | 266 | 34 | 0 |
| レース競技に参加するドライバーの装備品に関する細則 (2026) | 13 | 6,744字 | 122 | 11 | 11 | 10 |
| ラリー/スピード競技における安全ベルトに関する指導要綱 (2027) | 5 | 2,281字 | 57 | 20 | 13 | 2 |

本文・図版・表とも原本と突き合わせて一致を確認しました。とくに、
ベクタ図（ロールケージの断面図、HANS の取付角度図など）が
①②③④ の引き出し番号や「70mm以下」といった寸法注記ごと
1 枚の画像として本文の正しい位置に入ることを確認しています。

### 検証で見つけて直した問題

1. **1 行 = 1 段落になっていた**
   JAF の PDF は行ごとにテキストブロックが切られている。そのままだと
   1 行ごとに `<p>` が並んで読めず、RAG のチャンクも文の途中で切れる。
   「直前の行が右マージンまで達している／行送りが妥当／行頭に全角字下げも
   項番も無い」ときに繋ぎ直す処理を入れた。ぶら下げインデント（項番の幅だけ
   右にずれた継続行）も追随する。平均段落長が 43 字 → 61 字に改善。

2. **枠囲みの本文が画像になり、テキストから消えていた**  ← 影響大
   `［参考］ 国際モータースポーツ競技規則付則Ｌ項（抜粋）` のような
   罫線で囲んだ本文が、罫線をベクタ図と見なして丸ごと画像化されていた。
   その中の条文が全文検索にも AI の根拠にも出てこない状態だった。
   「枠内が文字で埋まっており、描画パスが枠線程度しか無い」領域は本文として
   扱うようにした（`is_framed_text`）。
   これだけでレース装備品細則の抽出文字数が **5,051 → 6,744 字（+34%）** に増えた。

3. **ヘッダ（柱）が章ごとに変わると除去できなかった**
   「第１章　一般規定」のような柱は章が変わると文字列も変わるため、
   出現ページ数の下限を全ページの半数ではなく 4 ページで頭打ちにした。
   本文より小さいフォントであることを別途要求しているので、
   本物の見出しを巻き込む危険は小さい。

4. 併せて、扉ページを誤って OCR 対象にする誤検知（文字数だけで判定していた）と、
   見出し行のない表の 1 行目が太字になる問題も修正した。

### 残っている改善余地

- `第 1 条` のように原本で字間が空いている見出しは、そのまま目次に出る。表示時に正規化したい。
- `9.4）…` のように項番から条文本体が続く行は見出しにせず本文に落としているが、
  項番は `clause` として各ブロックに保持しているので、AI 回答の出典表記には使える。
- 図版のサイズ実測: 43ページ・図34枚で約 1.1MB。JAF 全体（推定 8,000 ページ規模）では
  100〜200MB になる見込み。git でも当面は回るが、GCS 移設の判断材料になる。

## 11. 全件同期の結果（2026-09-09）

`python pipeline/cli.py sync` で JAF の全配布物を取り込みました。

| 項目 | 値 |
| --- | ---: |
| 文書 | 160 件（国内 125 / 国際 35） |
| ページ | 5,148 |
| 本文 | 5,713,603 字（うち表のセル 807,799 字） |
| 図版 | 1,489 枚 |
| 表 | 1,189 |
| 変換失敗 | **0 件** |
| 警告 | 13 ページ（全体の 0.25%） |
| 検索チャンク | 8,778 |
| `content/` | 101 MB |
| `data/search.db` | 56 MB |

カタログ件数はクローラの想定どおり国内 125 / 国際 35 でした。

### 全件で見つけて直した問題

1. **飾り罫で囲まれたページの本文が丸ごと画像化されていた**
   `is_framed_text` の判定をパス数主体にしていたのが原因。ページ全体を囲む
   飾り罫は装飾パスが十数本あり、「パスが 4 本以下」の条件で弾けなかった。
   判定を **枠内がどれだけ文字で埋まっているか** 主体に変更した。
   「オートテスト オーガナイザーガイドライン」は 6 ページ全体が画像になり
   本文 0 字だったが、7,146 字が取れるようになった。全体で本文 **+32,167 字**。

2. **表のセルを抽出文字数に数えていなかった**
   公認車両一覧・統計のように表が本体の文書が「抽出できていない」ように
   見えていた。検索インデックスには元から入っていたが、指標に出ていなかった。
   表のセルは全体で 807,799 字ある。

いずれも `pipelineVersion` を 0.2.0 に上げて全件を作り直しています。
1 ページあたりの抽出文字数は最小 191 字となり、ほぼ空の文書は無くなりました。

### 運用上わかったこと

- **再変換は `reconvert` で行う。** キャッシュ済み PDF から作り直すので
